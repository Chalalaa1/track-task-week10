# Design: ระบบติดตามงานทีม

เอกสารออกแบบจาก `plan.md` และ `requirements.md` สำหรับ US-1–US-4 และงานเสริม US-5–US-6 โดยใช้ Next.js 16 App Router + TypeScript + Tailwind, Supabase และ Vercel ตามโปรเจกต์ เป็นแบบสำหรับพัฒนา ยังไม่ใช่โครงสร้างที่ติดตั้งในฐานข้อมูลแล้ว

## 1. ภาพรวมและขอบเขต

เบราว์เซอร์แสดงหน้าจอและเรียก Supabase ด้วย publishable key (กุญแจสาธารณะที่ยังต้องผ่านสิทธิ์ผู้ใช้) ส่วน Next.js ฝั่ง server ตรวจผู้ใช้ด้วย `getUser()` หรือ `getClaims()` ก่อนทำรายการ ใช้ตัวเชื่อมเดิมใน `lib/supabase/` และ `proxy.ts` สำหรับต่ออายุ session (สถานะล็อกอิน) เก็บสถานะด้วย cookie เพื่อเปิดเบราว์เซอร์ใหม่ภายในวันเดียวกันได้ตาม AC-1.4

ฐานข้อมูลตรวจสิทธิ์ซ้ำด้วย RLS (กฎจำกัดการเข้าถึงแต่ละแถว) และกติกาฐานข้อมูลทุกครั้ง ไม่เชื่อรหัสผู้ใช้หรือบทบาทจากฟอร์ม ไม่ใช้ secret key ปิด Cache Components ตาม AGENTS.md และไม่เก็บผลข้อมูลส่วนตัวในแคชร่วมระหว่างผู้ใช้

US-1–US-4 เป็นงานหลัก US-5 และ US-6 ทำเมื่อมีเวลา ไม่มีหน้าจอแก้รายละเอียดหรือลบงาน ไม่มีออกจากทีม ย้ายทีม เปลี่ยนหัวหน้า หรือจัดการสมาชิก

## 2. Data model (โครงสร้างข้อมูล)

PK คือคีย์หลัก, FK คือคีย์อ้างอิง, unique คือห้ามซ้ำ ทุกคอลัมน์เป็น NOT NULL เว้นแต่ระบุว่า nullable ใช้ UUID เป็นรหัสและ `timestamptz` เก็บเวลาสากล

| ตาราง | คอลัมน์ | ชนิด | คีย์ / ค่าเริ่มต้น / เงื่อนไข |
|---|---|---|---|
| profiles | user_id | uuid | PK, FK → auth.users(id) |
| profiles | display_name | text | trim แล้วต้องไม่ว่าง |
| profiles | email | text | คัดลอกจาก auth.users.email โดยระบบ ไม่รับจากฟอร์มแยก |
| profiles | created_at | timestamptz | default now() |
| teams | id | uuid | PK, default gen_random_uuid() |
| teams | name | text | trim แล้วต้องไม่ว่าง |
| teams | owner_id | uuid | unique, FK → auth.users(id); หัวหน้าคนเดียว |
| teams | invite_code | text | unique, อักษร A–Z จำนวน 6 ตัว; สุ่มในฐานข้อมูล |
| teams | created_at | timestamptz | default now() |
| team_members | user_id | uuid | PK, FK → auth.users(id), FK → profiles(user_id); 1 คนมีได้ 1 แถว |
| team_members | team_id | uuid | FK → teams(id) |
| team_members | joined_at | timestamptz | default now() |
| tasks | id | uuid | PK, default gen_random_uuid() |
| tasks | team_id | uuid | FK → teams(id) |
| tasks | title | text | trim แล้วต้องไม่ว่าง |
| tasks | description | text | nullable |
| tasks | due_date | date | nullable; ไม่มีส่วนเวลา |
| tasks | assignee_id | uuid | FK → auth.users(id) |
| tasks | created_by | uuid | FK → auth.users(id); กำหนดจาก auth.uid() |
| tasks | status | text | default 'todo'; CHECK อยู่ใน todo / doing / done |
| tasks | created_at | timestamptz | default now() |
| tasks | updated_at | timestamptz | default now(); ระบบปรับเมื่ออัปเดต |

เพิ่ม unique `(team_id, user_id)` ใน team_members เพื่อให้ tasks ใช้ FK คู่ `(team_id, assignee_id)` อ้างถึง `(team_id, user_id)` ได้ จึงมอบงานให้คนนอกทีมไม่ได้แม้เรียกฐานข้อมูลโดยตรง เพิ่ม FK คู่ `(team_id, created_by)` เช่นเดียวกัน

บทบาทหัวหน้าคำนวณจาก `teams.owner_id = auth.uid()` สมาชิกอื่นเป็นสมาชิก ไม่เก็บบทบาทซ้ำใน profiles หรือ metadata ที่ผู้ใช้แก้ได้ ทีมหนึ่งมีสมาชิกหลายคนและงานหลายชิ้น ผู้รับงานหนึ่งคนมีหลายงานได้

ดัชนีสำหรับค้นข้อมูล: `team_members(team_id)`, `tasks(team_id, status)`, `tasks(assignee_id, due_date)` ส่วน PK และ unique มีดัชนีอยู่แล้ว ไม่กำหนดให้ชื่อทีม ชื่อที่แสดง หรือชื่องานห้ามซ้ำ ไม่คัดลอกรหัสผ่านลงตารางแอป และไม่เพิ่ม unique อีเมลซ้ำกับระบบ Auth

## 3. ตารางสิทธิ์สำหรับ RLS

เปิด RLS ทุกตารางใน public และกำหนดสิทธิ์ SQL ควบคู่กัน ตารางนี้แสดงสิทธิ์ของคำขอผู้ใช้โดยตรง คำว่า “ผ่านฟังก์ชัน” หมายถึงปิดการเขียนตรงและให้ใช้การทำรายการที่ตรวจสิทธิ์ในหัวข้อ 4 เท่านั้น

|---|---|---|---|---|---|
| profiles | anon / ยังไม่ล็อกอิน | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| profiles | เจ้าของข้อมูล แม้ยังไม่มีทีม | เฉพาะตนเอง | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| profiles | หัวหน้า / สมาชิกทีมเดียวกับเจ้าของ | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| profiles | ผู้ใช้อื่น / คนนอกทีม | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| teams | anon | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| teams | หัวหน้า / สมาชิกของทีม | ได้ รวมรหัสเชิญ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| teams | ผู้ล็อกอินที่ยังไม่มีทีม | ไม่ได้ | ผ่าน create_team | ไม่ได้ | ไม่ได้ |
| teams | คนนอกทีม | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| team_members | anon | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| team_members | หัวหน้า / สมาชิกทีมเดียวกัน | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| team_members | ผู้ล็อกอินที่ยังไม่มีทีม | ไม่ได้ | ผ่าน create_team / join_team | ไม่ได้ | ไม่ได้ |
| team_members | คนนอกทีม | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| tasks | anon | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| tasks | หัวหน้าทีมเจ้าของงาน | ได้ | ได้ | รายละเอียดและสถานะ ภายใต้กติกาฐานข้อมูล | ไม่ได้ |
| tasks | สมาชิกที่เป็นผู้รับงาน | ได้ | ไม่ได้ | เฉพาะ status | ไม่ได้ |
| tasks | สมาชิกทีมที่ไม่ได้รับงาน | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| tasks | คนนอกทีม รวมผู้ยังไม่มีทีม | ไม่ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |

การอ่าน profiles ใช้เงื่อนไขเป็นตนเองหรือมีทีมเดียวกันจริง ห้ามใช้เงื่อนไข “ทั้งคู่ไม่มีทีม” แล้วถือเป็นเพื่อนร่วมทีม การแก้ tasks ใช้ทั้ง USING (ตรวจแถวเดิม) และ WITH CHECK (ตรวจแถวใหม่) และ trigger ตรวจคอลัมน์ที่เปลี่ยน สิทธิ์หัวหน้าแก้รายละเอียดเป็นไปตาม plan.md แต่ไม่มีหน้าจอแก้ในรอบนี้ การลบผ่าน Table Editor เป็นการทำงานของผู้ดูแลฐานข้อมูลนอกสิทธิ์เว็บ ไม่เปิด DELETE policy ให้บัญชีผู้ใช้

## 4. ฟังก์ชันฐานข้อมูลและข้อมูลก่อนเข้าทีม

RPC คือการเรียกฟังก์ชันฐานข้อมูลจากแอป ฟังก์ชันที่ต้องข้าม RLS ใช้ SECURITY DEFINER (ทำงานด้วยสิทธิ์เจ้าของฟังก์ชัน) กำหนด `search_path` ว่าง อ้างตารางพร้อม schema และไม่ใช้ SQL ที่ประกอบจากข้อความผู้ใช้ ถอน EXECUTE จาก PUBLIC/anon ให้เฉพาะ authenticated ในฟังก์ชันที่ผู้ใช้ต้องเรียก และตรวจ `auth.uid()` ไม่เป็น null เสมอ ฟังก์ชันของ trigger ให้เรียกผ่าน trigger เท่านั้น

| ฟังก์ชัน | หน้าที่และข้อมูลที่คืน |
|---|---|
| handle_new_user() | trigger หลังสร้าง auth.users ตรวจชื่อที่แสดงจากข้อมูลสมัคร แล้วเพิ่ม profiles ในรายการเดียวกัน ถ้าบันทึกไม่สำเร็จให้ยกเลิกการสมัครทั้งหมด |
| sync_profile_email() | trigger เมื่ออีเมลใน Auth เปลี่ยน คัดลอกอีเมลจริงมายัง profiles ผู้ใช้เขียนทับอีเมลโดยตรงไม่ได้ |
| current_team_id() | คืนทีมของ auth.uid() หรือ null อ่าน membership ด้วยสิทธิ์ฟังก์ชันเพื่อหลีกเลี่ยง policy เรียกตัวเองวนซ้ำ ไม่รับ user_id ของคนอื่น |
| is_team_owner(team_id) | คืน boolean ว่าผู้เรียกเป็นหัวหน้าทีมนั้นหรือไม่ ไม่คืนรายละเอียดทีม |
| create_team(name) | ล็อกแถว profiles ของผู้เรียก ตรวจว่ายังไม่มีทีมและชื่อไม่ว่าง สุ่มรหัสเชิญ เพิ่มทีมและ membership หัวหน้าใน transaction เดียว (สำเร็จหรือย้อนคืนพร้อมกัน) คืน team_id |
| join_team(code) | ล็อกแถว profiles ของผู้เรียก ตรวจว่ายังไม่มีทีม trim และแปลงรหัสเป็นตัวใหญ่ ค้นรหัสและเพิ่ม membership ใน transaction เดียว คืน team_id เฉพาะหลังเข้าร่วมสำเร็จ |

create_team และ join_team ต้องล็อกแถวผู้ใช้เดียวกันเพื่อกันคำขอพร้อมกัน และมี PK ของ team_members เป็นด่านสุดท้าย ถ้ามีทีมแล้วคืน “คุณมีทีมอยู่แล้ว” ถ้ารหัสไม่ตรงคืน “ไม่พบทีมจากรหัสนี้” ไม่คืนชื่อ รหัส หรือรายชื่อสมาชิกก่อนเข้าร่วม ไม่ทำ endpoint สำหรับค้นหาทีมจากรหัสโดยเปิดอ่าน teams ทั้งตาราง ถ้ารหัสสุ่มชน unique ให้สุ่มใหม่โดยมีจำนวนครั้งสูงสุดและคืนข้อผิดพลาดเมื่อเกิน

## 5. กติกาที่บังคับในฐานข้อมูล

| กติกา | วิธีบังคับ | ข้อกำหนด |
|---|---|---|
| ชื่อที่แสดง ชื่อทีม ชื่องานไม่ว่าง | CHECK หลัง trim; ตรวจหน้าจอเพิ่มเพื่อแสดงข้อความไทย | US-1, AC-2.5, AC-3.5 |
| คนหนึ่งมีทีมเดียว สร้างทีมไม่ค้างครึ่งรายการ | PK membership + ล็อกแถว + transaction ของ RPC | AC-2.2–2.4 |
| หัวหน้าต้องเป็นสมาชิกทีมตัวเอง | create_team เพิ่มทั้งสองแถว และ FK คู่ (id, owner_id) → team_members(team_id, user_id) แบบ DEFERRABLE INITIALLY DEFERRED ตรวจตอน commit; ปิดเขียน membership/owner โดยผู้ใช้ | AC-2.2 |
| หัวหน้าเท่านั้นสร้างงานในทีมตน | INSERT policy ตรวจ owner, created_by = auth.uid(), status = todo | AC-3.1, AC-3.3 |
| ผู้รับงานต้องอยู่ทีมเดียวกับงาน | FK คู่ของ team_id/assignee_id | AC-3.4 |
| ผู้รับงานแก้ได้เฉพาะสถานะ | BEFORE UPDATE trigger เปรียบเทียบ OLD/NEW ทุกคอลัมน์ธุรกิจ ถ้าไม่ใช่หัวหน้าและมีการเปลี่ยนอย่างอื่นให้ปฏิเสธ | AC-4.3–4.4 |
| หัวหน้าแก้ข้อมูลงานได้เฉพาะในทีม | policy + FK คู่; trigger ห้ามเปลี่ยน id, team_id, created_by, created_at ทุกบทบาท และให้ระบบตั้ง updated_at เอง | US-3–US-4 |
| มีสถานะเพียงสามค่า | CHECK status; ยอมให้เปลี่ยนกลับไปค่าใดก็ได้ในสามค่า | AC-4.1 |

ไม่เก็บสถานะ “เลยกำหนด” ลงฐานข้อมูล คำนวณจาก `due_date < วันที่ปัจจุบันใน Asia/Bangkok AND status <> 'done'` วันที่ครบกำหนดยังไม่ถือว่าเลยกำหนด งานไม่มี due_date ไม่แสดงป้าย อนุญาตวันย้อนหลังตามกรณี AC-4.5

## 6. หน้าจอและเส้นทาง

| route (ที่อยู่หน้าเว็บ) | เนื้อหาและการทำงาน | user story |
|---|---|---|
| `/` | คงหน้าตรวจการเชื่อมต่อเดิมและเพิ่มลิงก์เข้าใช้งานได้ | ทางเข้าระบบ |
| `/login` | สมัครด้วยชื่อ อีเมล รหัสผ่านอย่างน้อย 6 ตัว / ล็อกอิน; สมัครสำเร็จไป /team | US-1 |
| `/team` | ไม่มีทีม: สร้างหรือเข้าร่วม; มีทีม: ชื่อ รหัสเชิญ รายชื่อและบทบาท พร้อมลิงก์งาน | US-2 |
| `/tasks` | งานทุกชิ้นของทีมแยก todo / doing / done; ฟอร์มสร้างงานเฉพาะหัวหน้า; ตัวเลือกสถานะสำหรับผู้รับงานและหัวหน้า | US-3, US-4, US-6 เสริม |
| `/my` | กรอง assignee_id = auth.uid(); ซ่อน done เริ่มต้น มีตัวเลือกแสดง; เปลี่ยนสถานะตามสิทธิ์เดิม | US-5 เสริม, US-4 |

ทุกหน้าที่ต้องล็อกอินตรวจฝั่ง server ถ้าไม่มี session ไป /login ผู้ไม่มีทีมเปิด /tasks หรือ /my ไป /team แถบด้านบนแสดงชื่อผู้ใช้ ลิงก์ทีม งานทีม งานของฉันเมื่อทำ US-5 และปุ่มออกจากระบบซึ่งล้าง session แล้วไป /login

การ์ดงานแสดงชื่อ รายละเอียดเมื่อมี ชื่อผู้รับงาน วันกำหนดส่งรูปแบบไทยหรือ “ไม่มีกำหนด” และป้ายแดงพร้อมคำว่า “เลยกำหนด” บันทึกสถานะสำเร็จแล้วดึงข้อมูลใหม่หรือย้ายการ์ดในหน้าปัจจุบัน ถ้าล้มเหลวคงสถานะเดิมและแสดงข้อผิดพลาด ไม่กำหนดให้เครื่องของสมาชิกคนอื่นอัปเดตสดอัตโนมัติในรอบนี้

หน้า /my เรียง due_date จากน้อยไปมาก null ไว้ท้าย ใช้ created_at และ id เป็นลำดับรองให้ผลคงที่ เมื่อไม่มีงานตรงตัวกรองแสดง “ยังไม่มีงานที่ได้รับมอบหมาย” และลิงก์ /tasks; ทีมไม่มีงานใช้ “ยังไม่มีงานในทีม” ตาม AC-3.6

ทุกหน้ามีสถานะกำลังโหลด ไม่มีข้อมูล และผิดพลาดเป็นไทย ฟอร์มมีป้ายชื่อช่องและข้อความผิดพลาด อ่านและกดได้ด้วยคีย์บอร์ด ระหว่างบันทึกปิดปุ่มส่งซ้ำ หน้าจอตั้งแต่ 375px ไม่ล้นแนวนอน และบอร์ดสามคอลัมน์เรียงลงมาเมื่อจอแคบ (NFR-3–4)

## 7. ลำดับสร้างงานและอีเมล (US-6 งานเสริม)

1. Server Action (ฟังก์ชันรับคำขอฝั่งเซิร์ฟเวอร์) ตรวจผู้ใช้จริงและตรวจข้อมูล ส่ง INSERT ด้วย Supabase client ของผู้ใช้ ให้ RLS และ constraint ตรวจอีกชั้น
2. หาก INSERT ไม่สำเร็จ หยุดโดยไม่ส่งอีเมล หากสำเร็จรับ id งานที่บันทึกแล้ว งานต้องยังอยู่แม้ขั้นตอนส่งเมลล้มเหลว
3. ในคำขอสร้างงานเดียวกัน อ่านงาน ทีม ชื่อผู้มอบหมาย และอีเมลผู้รับจาก profiles ด้วยสิทธิ์หัวหน้าในทีม ไม่รับที่อยู่อีเมลปลายทางจากคำขอ ไม่เปิด endpoint ส่งเมลจาก task_id อิสระ
4. ส่ง Gmail SMTP จาก server ภายในกรอบ 1 นาทีของ AC-6.1 กำหนด timeout การเชื่อมต่อและส่งรวมต่ำกว่า 1 นาที ไม่ปล่อยงานส่งเมลแบบไม่รอผลหลังจบคำขอ ใช้บัญชีทดลองและ `GMAIL_USER`, `GMAIL_APP_PASSWORD` เฉพาะ server ตามข้อกำหนด
5. หัวเรื่อง “งานใหม่: <ชื่องาน>” เนื้อหามีชื่องาน วันกำหนดหรือ “ไม่มีกำหนด” ชื่อทีม และชื่อผู้มอบหมาย ใช้ข้อความล้วนหรือ escape ข้อมูลก่อนใส่ HTML ถ้าส่งพลาดคืน “สร้างงานแล้ว แต่ส่งอีเมลแจ้งไม่สำเร็จ” ห้ามให้ผู้ใช้กดสร้างงานซ้ำเพื่อส่งเมลใหม่

แบบ workshop ใช้การส่งทันที ไม่มีคิวหรือส่งซ้ำอัตโนมัติ การรับเมลภายใน 1 นาทีขึ้นกับบริการภายนอกด้วย หาก server หยุดหลังบันทึกงานอาจไม่มีอีเมล ต้องตรวจ AC-6.1 บนสภาพแวดล้อมจริงเมื่อทำ US-6 ไม่เพิ่มตารางอีเมลในงานหลัก

## 8. สมมติฐานและลำดับพัฒนา

ใช้สมมติฐานเดิมใน plan.md: สมาชิกทุกคนเห็นรหัสเชิญ หัวหน้ารับงานเองได้ งานมีผู้รับคนเดียว และวันกำหนดส่งยึดประเทศไทย ไม่มีข้อขัดแย้งที่ต้องเปลี่ยนสิทธิ์จากเอกสารต้นทาง

ตัวเลือกออกแบบที่ปรับได้: รหัสเชิญใช้ A–Z ตัวใหญ่, ไม่จำกัดลำดับเปลี่ยนสถานะ, ข้อมูลทีมของเครื่องอื่นแสดงล่าสุดเมื่อโหลดใหม่ และใช้ลำดับรอง created_at/id ใน /my การเปลี่ยนตัวเลือกเหล่านี้ไม่ต้องแก้ขอบเขตงานหลัก

ทำ US-1 → US-2 → US-3 → US-4 แล้วจึง US-5 → US-6 เขียนการเปลี่ยนฐานข้อมูลเป็นไฟล์ใน `supabase/migrations/` ให้ผู้ใช้รันใน SQL Editor ตาม AGENTS.md เริ่ม US-1 ด้วย profiles, trigger สมัครผู้ใช้, RLS เจ้าของข้อมูล และหน้า /login จากนั้นเพิ่มสิทธิ์อ่าน profiles ของเพื่อนร่วมทีมเมื่อทำ US-2

ใช้ AC ใน requirements.md เป็นรายการตรวจรับภายหลัง โดยเฉพาะบัญชี A/B/C สำหรับแยกทีม คำขอแก้คอลัมน์โดยตรง คำขอเข้าทีมพร้อมกัน และวันกำหนดตามประเทศไทย คำสั่งโครงการที่มีจริงคือ `npm run dev`, `npm run lint`, `npm run build` ยังไม่มีคำสั่งทดสอบอัตโนมัติใน package.json
